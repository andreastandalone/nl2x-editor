# Coding standards

Rules every change must follow. Reviewers enforce them; agents read them before writing code.

## Layout

```
engine/            the engine: plain C++20, no JUCE, no GUI, no threads of its own
  include/nl2x/    the engine's public headers (the only thing the shell may include)
  src/             implementation
plugin/            the JUCE shell: AudioProcessor, editor, MIDI port handling
tests/             automated tests (Catch2) and the simulated Nord Lead 2X
  sim/             SimulatedNordLead2X
  fixtures/        our own .syx fixtures with known values
tools/             developer scripts (pluginval, fixtures generation)
```

## The engine

- **No JUCE, no platform headers** in `engine/`. Only the C++ standard library. This keeps the engine portable (Windows port) and testable.
- **The engine has one seam: MIDI bytes.** It receives complete MIDI messages through a single entry point and sends them through a single output interface. Time reaches it only as explicit calls carrying a timestamp (milliseconds); it never reads a clock and never sleeps. The file system is reached through the standard library, under paths the caller passes in.
- **Single-threaded.** The shell calls the engine from one thread (the message thread). The shell owns threading: MIDI input callbacks are queued and delivered on that thread.
- **Unverified hardware behaviour lives in one place:** `engine/include/nl2x/HardwareAssumptions.h`. Every constant or rule there names the research fact it rests on and whether it is verified on hardware. Code and simulator use these names; nothing else hard-codes a guessed value. When hardware discovery (#3) settles a point, change it there.
- **Never clamp or "fix" values from dumps.** Unknown and out-of-range bytes round-trip unchanged (spec, research §3).
- **The type byte of a received Bank dump is never used as a storage location.**

## Tests

- Tests drive the engine as the shell does (parameter changes, user actions, project load, incoming MIDI) and assert only on what crosses the MIDI boundary and on files written. **Never assert on engine internals.**
- The simulated synth (`tests/sim/`) behaves as the real synth does according to the research document and `HardwareAssumptions.h`. It can be told to misbehave (no SysEx answer, no CC echo, wrong Global Channel) to test diagnostics.
- Tests against the official factory Banks are skipped unless the files exist under `docs/research/factory-bank/`; they are never committed.
- Every change keeps `ctest` green.

## Style

- C++20, `namespace nl2x`. Types `PascalCase`, functions and variables `camelCase`, constants `kPascalCase`, files named after their main type.
- Headers carry short comments that explain *why*; no comments restating the code.
- Use the terms of [GLOSSARY.md](GLOSSARY.md) in names: `Slot`, `Program`, `PercussionKit`, `Performance`, `Bank`, `EditBuffer`, `MorphAmount`, `SlotChannel`, `GlobalChannel`, `Library`, `Audition`. Avoid the synonyms the glossary lists.
- User-visible strings in English, with the manual's terms.

## Third-party material

Never commit Clavia manuals, factory Banks, reference screenshots or anything from the AURA Plugins editor (ADR 0002). Fixtures are generated by our own code with values we chose.
